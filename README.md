# SkillSwap

Проект для практики командной разработки на **React + TypeScript + Vite**.  
Создан и развивается **когортой 37 — самой мощной и дружной! 💪**

---
## Взможно, пригодится
```
    npm install clsx
    npm i redux react-redux @reduxjs/toolkit
    npm i react-router-dom
    npm i -D @types/react-router-dom
    npm i --save-dev @types/node
```

## Быстрый старт

1. Подготовка:
    ```bash
    npm install
    ```

2. Запустите проект в режиме разработки:
    ```bash
    npm run dev
    ```

3. Откройте в браузере:
    👉 [http://localhost:3000/](http://localhost:3000/)

4. Проверьте стиль кода:
    ```bash
    npm run lint
    ```

## Логика проекта (как реализовано сейчас)

### 1) Источник данных

- Проект работает на локальных JSON-файлах из `public/db`.
- Основные сущности:
    - `users.json` — пользователи и их навыки.
    - `offers.json` — предложения обмена.
    - `likes.json` — лайки между пользователями.
    - `places.json`, `skills_categories.json`, `skills_subcategories.json` — справочники.
- API-слой находится в `src/api/Api.ts` и использует `fetch(...)` к JSON.

### 2) Инициализация приложения

- При старте `App.tsx` диспатчит загрузку:
    - офферов,
    - пользователей (обычных, популярных, новых по дате, случайных),
    - городов,
    - категорий и подкатегорий.
- Если есть текущий пользователь (`state.user.user`), загружаются его лайки.

### 3) Роутинг

Текущие основные маршруты:

- `/` — главная (`HomePage`).
- `/skills` — каталог (упрощенный экран с `FilterSection + GridList`).
- `/skills/:id` — страница оффера (`OfferPage`).
- `/auth/login`, `/auth/register` — формы входа/регистрации.
- `/registration/step1..3` — пошаговая регистрация.
- `/profile` — личный кабинет (вкладки внутри одной страницы).
- `/favorites`, `/requests` — заглушки.
- `/about`, `/500`, `*`.

Важно: role-based guards пока не реализованы. Маршруты не ограничиваются по ролям.

### 4) Авторизация и сессия (текущее поведение)

- Полноценного backend-login нет.
- Кнопка «Войти» в `Header` выбирает случайного пользователя из уже загруженного списка и кладет его в `state.user.user`.
- Выход (`logoutThunk`) просто очищает текущего пользователя в сторе.
- Регистрация (модалка/шаги) собирает данные формы, но не создает нового пользователя в `users.json` и не логинит его через API.

### 5) Redux-состояние

Корневой стор содержит слайсы:

- `user` — текущий пользователь, его лайки, текущие офферы в профиле.
- `users` — общий список пользователей + `offerUser` (тот, кому открыли карточку обмена).
- `popularUsers`, `createdAtUsers`, `randomUsers` — отдельные подборки для главной.
- `filteredUsers` — результаты фильтрации.
- `filters` — тип навыка, пол, города, подкатегории, текстовый запрос.
- `offers` — список офферов + флаг создания оффера.
- `notification` — события уведомлений, seen/unseen.
- `categories`, `places` — справочники.

### 6) Главная страница и фильтры

- На главной (`HomePage`) есть два режима:
    - если фильтры пустые — показываются 3 ленты: популярные, новые, рекомендуем;
    - если фильтры активны — показываются только `filteredUsers`.
- Поиск в `Header` диспатчит `applySearchQuery` (debounce 300ms):
    - пишет `q` в `filters`,
    - вычисляет подкатегории по тексту,
    - перезапрашивает `filteredUsers`.
- Фильтрация в API поддерживает:
    - пол,
    - города,
    - тип навыка (`all/can_teach/want_to_learn`),
    - подкатегории,
    - текст (от 3 символов).

### 7) Карточка пользователя, лайки, переход в оффер

- `UserCard`:
    - лайк переключается локально (`toggleLikeAction`) в списках `users` и `filteredUsers`;
    - при клике «Подробнее» сохраняется `offerUser` в стор и выполняется переход на `/skills/:id`.
- В `GridList` текущий авторизованный пользователь скрывается из списка.

### 8) Офферы и уведомления

- `OfferPage` берет цель обмена из `state.users.offerUser`.
- Кнопка «Предложить обмен»:
    - если пользователь авторизован — диспатчит `addOfferThunk` (имитация создания оффера);
    - если не авторизован — открывает модалку регистрации.
- Уведомления (`NotificationWidget`) строятся на клиенте из `offers + currentUser`:
    - новый входящий оффер,
    - принятие моего оффера,
    - мой оффер еще не принят.
- Есть массовые действия: «прочитать все», «очистить просмотренные».

### 9) Профиль

- `/profile` — единая страница с вкладками.
- Вкладка `personal` показывает персональные данные.
- Остальные вкладки в основном содержат onboarding-заглушки.

### 10) Ограничения текущей логики (важно для редизайна и ролей)

- Нет поля роли в модели пользователя (`TUser`).
- Нет защищенных маршрутов и проверки прав.
- Нет реального login/register/logout через backend.
- Часть страниц является заглушками.
- Взаимосвязь оффера использует `offerUser` из стора (зависит от перехода через карточку).

## Что нужно учесть в новом ТЗ (для генерации нового макета)

Чтобы редизайн и новые страницы были реализуемыми, в ТЗ для нейросети нужно явно зафиксировать:

1. Три роли: `guest`, `user`, `admin` и отдельные состояния интерфейса для каждой роли.
2. Role-based навигацию и доступ к страницам (guards + скрытие пунктов меню).
3. Новую структуру страниц:
     - публичные,
     - пользовательские (личный кабинет, избранное, заявки, уведомления, настройки),
     - админские (dashboard, пользователи, контент, модерация, системные настройки).
4. Единые состояния экранов: loading, empty, error, success.
5. Миграцию текущих сущностей (`users`, `offers`, `likes`, `categories`, `places`) без потери бизнес-смысла.
6. Переиспользуемые компоненты UI-kit и адаптивность desktop/tablet/mobile.

Если нужно, можно следующим шагом сделать отдельный раздел README с целевой технической логикой внедрения ролей (модель пользователя, guards, матрица прав и минимальные изменения в Redux/API).

## ТЗ на создание нового макета (редизайн + роли)

Этот блок можно копировать в нейросеть как техническое задание на UI/UX-макет.

### 1) Цель

Сделать новый макет приложения SkillSwap с role-based интерфейсом для 3 ролей:

1. Гость (guest).
2. Пользователь (user).
3. Администратор (admin).

Макет должен сохранить текущую бизнес-логику проекта (каталог навыков, карточки пользователей, офферы, фильтры, уведомления, профиль), но расширить ее новыми страницами и навигацией по ролям.

### 2) Общие требования к макету

1. Для каждой страницы показать desktop и mobile версии.
2. Для ключевых экранов показать состояния: loading, empty, error, success.
3. Добавить role-based состояния в навигации: какие пункты меню видит каждая роль.
4. Подготовить UI-kit: кнопки, поля ввода, фильтры, карточки, модалки, таблицы, бейджи ролей, уведомления.
5. Учитывать текущие сущности данных: users, offers, likes, categories, subcategories, places.

### 3) Страницы по ролям

#### 3.1 Гость (guest)

Гость видит только публичную часть и не имеет доступа к личным и админским разделам.

Обязательные страницы guest:

1. Главная страница (`/`).
2. Каталог навыков/пользователей (`/skills`) с фильтрами.
3. Страница предложения/навыка (`/skills/:id`) в режиме просмотра.
4. О проекте (`/about`).
5. Вход (`/auth/login`).
6. Регистрация (модалка и/или шаги `registration/step1..step3`).
7. 404 (`*`).
8. 500 (`/500`).

Ограничения guest в макете:

1. Кнопки действий, требующих авторизацию, показывать как CTA на вход/регистрацию.
2. Не показывать пункты меню: профиль, избранное, заявки, уведомления, админ-панель.

#### 3.2 Пользователь (user)

Пользователь видит все публичные страницы + личный кабинет и рабочие разделы обмена.

Обязательные страницы user:

1. Все страницы guest.
2. Личный кабинет (основная страница профиля) (`/profile`).
3. Персональные данные профиля (`/profile/personal` или вкладка внутри `/profile`).
4. Мои заявки (`/profile/requests` или `/requests`).
5. Мои обмены (`/profile/exchanges`).
6. Избранное (`/profile/favorites` или `/favorites`).
7. Мои навыки (`/profile/skills`).
8. Уведомления (`/profile/notifications` и/или popover-виджет).
9. Настройки аккаунта (новая страница, например `/profile/settings`).
10. Чат (список диалогов) (`/chat`).
11. Чат (экран диалога) (`/chat/:dialogId`).

Функциональные акценты user в макете:

1. Лайк/анлайк карточек.
2. Предложить обмен со страницы навыка.
3. Просмотр входящих и просмотренных уведомлений.
4. Быстрый переход из уведомления в релевантный сценарий.
5. Обмен сообщениями в чате после создания/принятия оффера.
6. Состояния чата: пустой список диалогов, активный диалог, непрочитанные, отправка, ошибка отправки.

#### 3.3 Администратор (admin)

Администратор видит все страницы user + административный контур управления платформой.

Обязательные страницы admin:

1. Админ-дашборд (`/admin`).
2. Управление пользователями (`/admin/users`).
3. Карточка/редактирование пользователя (`/admin/users/:id`).
4. Управление офферами/обменами (`/admin/offers`).
5. Модерация контента (`/admin/moderation`).
6. Категории и подкатегории навыков (`/admin/skills-taxonomy`).
7. Управление справочником городов (`/admin/places`).
8. Системные уведомления/логи (`/admin/notifications` или `/admin/logs`).
9. Настройки платформы и ролей (`/admin/settings`).
10. Админ-раздел чатов (`/admin/chats`) для модерации диалогов и жалоб.

Функциональные акценты admin в макете:

1. Табличные представления с фильтрами, сортировкой и поиском.
2. Массовые операции (модерация, блокировка, смена статусов).
3. Явная индикация критичных действий (danger zone).
4. Инструменты модерации чатов: поиск диалога, просмотр истории, скрытие/блокировка.

### 3.4 Чат (обязательный модуль)

Чат должен быть отдельным блоком в макете и входить в основной пользовательский сценарий обмена.

Обязательные экраны чата:

1. Список диалогов (`/chat`).
2. Экран переписки (`/chat/:dialogId`).
3. Пустое состояние: нет диалогов.
4. Техническое состояние: нет соединения/ошибка отправки.

Обязательные элементы UI чата:

1. Список диалогов: имя собеседника, последнее сообщение, время, индикатор непрочитанного.
2. Окно сообщений: входящие/исходящие пузыри, дата-разделители, статус сообщения.
3. Поле ввода: текст, отправка, disabled-состояние.
4. Переход в профиль собеседника и в карточку оффера из диалога.

### 4) Навигация и доступы

1. Header для публичной зоны и user-зоны.
2. Отдельная admin-навигация (sidebar + верхняя панель).
3. Страницы admin недоступны для guest/user.
4. Личные страницы недоступны для guest.
5. Для запрещенных переходов показать экран 403 (новая страница) и предложить доступные действия.

### 5) Что должно быть на выходе от нейросети

1. Sitemap с разделением по ролям guest/user/admin.
2. User flow минимум для 3 сценариев:
    1. Guest -> Login/Register -> User.
    2. User -> Открыть карточку -> Предложить обмен -> Уведомление.
    3. User -> Предложить обмен -> Открыть чат -> Отправить сообщение.
    4. Admin -> Модерация контента/чата -> Смена статуса.
3. Wireframe всех обязательных страниц.
4. High-fidelity макеты ключевых страниц.
5. UI-kit и правила поведения компонентов в разных состояниях.

### 6) Критерии приемки макета

1. Все страницы по ролям из раздела 3 присутствуют.
2. Есть четкое разделение прав по ролям в навигации и на экранах.
3. Публичные и приватные сценарии визуально и логически различимы.
4. Макет покрывает текущую логику проекта и готов к передаче в разработку.
5. Чат присутствует как обязательный пользовательский сценарий и как отдельный набор экранов.
